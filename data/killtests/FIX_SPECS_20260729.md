**Evidence (exact, from the decision archive).** AMIX 7/29 09:32 `reclaim_shadow_fire`:
`price 4.62, stop 4.6512` — the stop sat **ABOVE** the fire price. Risk-per-share was NEGATIVE.

so X cannot occur; if shorts are ever added this guard must become side-aware.

away → pin must go RED.

Also feeds the RTH monitor for positions carried from the open.

## P1-F · `_clear_open_trade` must verify; orphan recovery must reject hollow rows

**Evidence.** After my restart, the dashboard held a **ghost STFS open-position row with entry,
entry_date and trade_id all `None`**, while the bot reported `positions now 0` and the trade was
correctly booked at 10:41:15. Cause: `_clear_open_trade` ([:2000]) swallows all exceptions and never
checks the response code — a failed clear is SILENT. Auth was not the issue (both services fall back
to the same `DASHBOARD_SECRET` default). Danger: `_recover_orphaned_trades` reads
`_load_open_trades_from_screener()` on EVERY boot, so a hollow row would be "recovered" again —
possibly booking a duplicate or erroring on the nulls. Cleared manually at Marcos's instruction
(verified: open_trades 0, trades still 21, STFS −$27.84 intact).

**Fix.** (1) `_clear_open_trade` checks the status code, re-reads `/api/open_trades`, retries once,
and logs LOUDLY if a row survives. (2) `_recover_orphaned_trades` discards any row lacking
entry/entry_date/trade_id with a `orphan_row_invalid` warning instead of recovering it.

**Wrong when X:** a legitimately-mid-write row is discarded and a real position goes unrecovered.
Mitigation: discard only when ALL identifying fields are null, and always log.

**Rig pin:** hollow row → discarded + warned; valid row → still recovered (the BOXL-class protection
must survive).
